## Probe (S2) and the STOP

- **The window cap is 30 calendar days.** Probes 1 (AAPL 2025, default), 2 (`extended=true`), 4 (NVDA 2024–2025)
  and 5 (NVDA 2024) each came back with only the last 30 calendar days of their window ending at `to`, every
  session in them complete (AAPL 2025: 267 regular bars, 2025-12-02 … 12-31; 2025-12-01, a Monday, missing).
  The `extended` answer had 666 rows over the same days, so the cap counts days, not rows, as ATOM IR-04 found
  at 1 minute (3 days). `probe.day_bounds` turns each truncated answer into bounds on the day count; they
  intersect at [30, 30], and IR-04's whole 30-day answer (2023-12-21 … 2024-01-19) corroborates it.
- **Projection at 30 days:** 16,833 requests for the plan as first written, 14,003 for the PRD's own span (from
  2024-06-03), 4,000 for the test period alone, against 2,995 left. The probe recorded `stop` and the fetch
  refused to start (PRD S2: STOP and report).
- **Operator decision (2026-10-27, asked in session):** two more requests to check the legacy `/api/v3`
  endpoint; if it has the same cap, raise the FMP cap to 17,000 for the full design. v3 answered the same 30
  days (one request; the second was not needed). The cap is now 17,000 (`configs/project.yaml`; §15 row 1).
- **A bug in the first probe run.** The pre-market share was divided by the 250 expected sessions instead of
  the 21 served ones, so `extended` read as not served and probes 4–5 went out with `nonadjusted=true` only.
  The cap finding does not depend on it (probes 1 and 2 cover the same days). The code now divides by the
  served sessions and defines probes 4–5 without `extended` (the cap counts days); the re-runs read the cache
  and sent nothing. `extended` and `nonadjusted` were never probed together; the fetch's pre-flight did it.

- **Span:** bars from 2024-01-02, not 2024-06: σ_30 and σ_rest need 60 of the 126 sessions ending t−1
  (PREREG §5.4). From 2024-06-03 they would be missing for train sessions before about 2024-08-28; from
  2024-01-02 they have 124 sessions at the train start. A joiner's bars start 126 sessions before its first
  member session, a public span starts no earlier than the symbol's first EOD day, and a symbol's span ends at

- **Windows:** 30 calendar days, each starting on a session and ending on the last session within 30 days of
  its start (15,848 instead of 16,833 for plain 30-day windows), cut at the val-B / test boundary so that no
  answer holds both public and test-period bars.

## Client and ledger (S1)

- One `request` line before every HTTP attempt (`FmpLedger.reserve`, which refuses request cap + 1) and one
  `response` line after it with status, rows and bytes. Only `request` lines count toward the cap, so a request
  that never returns still counts. Retries are new requests and are reserved again.
- Public answers are cached as the vendor's text (gzip JSON, keyed by the sha256 of interval + parameters).
  A window that reaches the test period is never cached outside the sealed directory (`FmpClient._cacheable`).
- The key is read from the environment or `.env` and sent as `apikey`; httpx exceptions (which carry the URL)
  are reduced to their class name; vendor error text is scrubbed of the key. Tests check the ledger and the
  cache never hold it.

## Price basis (S4)

FMP's `nonadjusted=true` levels are as traded across splits (NVDA, AVGO, WMT, CMG pass), but several histories
sit on a constant factor up to a corporate action. Each session's basis is therefore decided per session, with
what is known at 10:00 (§15 row 3): the level is the median EOD close / last-bar close of the symbol's previous
5 sessions, confirmed by the session's own EOD open / first-bar open. Using the session's own close (the first
version) would have let a post-10:00 price into P_10:00; anchoring on the session's open (S4's wording) would
let a misprinted first bar set the factor (April 2025: AJG, AON, AMP, AVY first-bar opens 5–18% off).

## D1 quantities (S5) and reactions / targets (S6)

- The arithmetic of G_D1, G^lvl, the 10:00 rung and the D1 targets is in `panel/reactions.py` and
  `panel/targets.py`, hashed at the freeze; `bars.derive` builds their inputs, as `panel.build` does for D2.
- G^lvl_D1 and CAR^lvl_10 are the same number (A1.2 defines both as AR(close(prev) → 10:00) / σ_cc,t); both
  columns are stored, `car_lvl_10` registered `post` like the other rungs, `g_d1_lvl` `d1`.
- The test route reads the blinded bars first (`lock.read_sealed(bars30_2026, …)`), so the refusal before the
  freeze is logged under the bars' name.

## D1 states (S6)

- Call B on W0 news is the D1 state (`StateSpec.decision_point`). Every W0 exclusion applies: the D1 state is
  decided at 10:00, before the close, so the running-story rule (written for W0 because running stories carry
  the session's outcome) protects it as it protects D0; explainers, TradingView and non-English articles are in
  no state anyway.
- `reaction_so_far` at D1 reads `d1` columns only (`validate_spec`). Moves are in typical close(prev) → 10:00
  moves: a new codebook unit `d1` ("a typical move by this time of day"; E4 "same-time-of-day"), because "a
  typical day's move" would misstate G_D1 by about 1/0.7.
- The news list is re-fitted to Call B's longest core question and the longest D1 reaction block, so it can be
  shorter than the Call A D0 list of the same event; the Call A D0 states are not rebuilt (they are cached by
  sha256 downstream).
